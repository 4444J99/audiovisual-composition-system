# Migration 2.1.0: functional software identities

This migration extends the workspace-root contract without moving physical
checkouts, source media or archives. Its brief is
[the naming and responsibility contract](../naming-responsibility-contract.md).

## Execution plan

1. Verify authenticated repository identity, current visibility, authority and
   existing open/merged work. Use exact base commits and isolated topic branches.
2. Extend `workspace-manifest.json` with typed identities and functional
   directory names. Keep project IDs/slugs and repository IDs as stable aliases.
   Validate type/reference agreement and deny new private bindings in this public
   coordination owner.
3. Update `tools/workspace_layout.py` and `tools/identity_contract.py` to render
   functional navigation and compatibility records from the same manifest.
   Generate the catalog deterministically and omit private source relationships.
4. Add each implementation's `ace-manifest.json`. Where live reusable APIs carry
   artwork names, add functional entrypoints backed by the same objects. Separate
   postproduction composition records from the reusable package with a neutral
   composition path and old-path compatibility. Preserve historical imports,
   source bytes, archive names, native IDs and shared-engine pins.
5. Run catalog, type/reference, privacy, interface compatibility, source-digest
   and synthetic second-composition tests. Independently review the actual diffs.
6. Publish connected draft PRs against their owning repositories and read back
   exact heads. A stacked change targets the existing feature branch rather than
   duplicating that feature against main. Record CI state truthfully.

## Review focus

- A title alias must not reclassify a software project as an artwork.
- Composition path changes must not break relative media or qualification refs.
- Functional facades must preserve object identity and legacy CLI behavior.
- Public generation must not serialize private Page, source or repository links.
- A metadata-only normalization must not rewrite pinned playback runtime bytes.

## Apply

```sh
python3 tools/workspace_layout.py render
python3 tools/workspace_layout.py check --catalog-only
python3 -m unittest discover -s tools/tests -v
node --test tools/tests/test_verify_tmb_composition.cjs
# With authenticated GitHub access:
python3 tools/verify_repository_access.py --github
```

`render` changes tracked derived documents only. Workstation `apply` retains its
existing collision checks and ignored local links, and must run only where the
declared source checkouts already exist. Cloud validation uses `--catalog-only`;
no workstation or media validation is implied.

## Rollback

Revert the migration commit in its owning repository and regenerate the old
catalog with that revision's tool. Since source locations and IDs were retained,
no media or Git history needs to move back. Generated new functional directory
views can be removed only after confirming they contain solely generated files;
never delete or traverse a source link as cleanup. Existing implementation
imports and legacy composition paths remain supported during adoption. Revert
implementation facade/metadata commits independently, retaining the original
feature/evolution commits underneath them.

## Known boundary

The coordination repository remains public. Redacting current generated views
does not retract legacy published manifests or historical evidence. New private
source relationships are excluded from this migration. No repository rename,
visibility change, source upload, edition publication or merge is implied.
